# إتقان المقاس — منصة إدارة طلبات الكراتين

منصة ويب عربية (RTL بالكامل) تستبدل ملف الإكسل بنظام متعدد المستخدمين:
مندوبون لكل واحد حسابه، ومشرف يرى الجميع، مع حساب تلقائي للأرباح والعمولات
والضريبة.

## المكدّس التقني

| الطبقة | التقنية |
|---|---|
| الواجهة | Next.js 15 (App Router) + TypeScript + Tailwind CSS |
| الحالة | React Server Components + Server Actions |
| قاعدة البيانات | PostgreSQL على Supabase |
| المصادقة | Supabase Auth (بريد + كلمة مرور) |
| الصلاحيات | Supabase Row Level Security |
| المرفقات | Supabase Storage (حاوية خاصة، روابط موقّعة) |
| الرسوم البيانية | Recharts |
| التصدير | exceljs للإكسل + طباعة المتصفح لـ PDF |
| الخط | Cairo من Google Fonts |

### تجهيز قاعدة البيانات

طبّق ملفات `supabase/migrations/` بالترتيب الرقمي (عبر Supabase CLI أو محرر
SQL في لوحة Supabase):

```bash
supabase db push          # أو نفّذ كل ملف يدويًا بالترتيب
```

ثم أنشئ أول حساب مشرف من لوحة Supabase Auth مع `user_metadata`:

```json
{ "full_name": "أبو أيمن", "role": "admin", "share_pct": 50 }
```

trigger في `0010_auth_trigger.sql` ينشئ صفّه في `public.users` تلقائيًا. بعدها
يستطيع المشرف إنشاء حسابات المندوبين من شاشة **المستخدمون**.

### اختبارات العزل على قاعدة بيانات حقيقية

اختبارات القسم 11 الإلزامية تعمل على Postgres محلي عبر محاكاة بيئة Supabase
(`auth.uid()`، دور `authenticated`، جداول `storage`):

```bash
# شغّل Postgres محليًا ثم:
PGHOST=/tmp PGPORT=5433 PGUSER=postgres npm run test:db
```

ما يتحقق منه فعليًا (وليس بالواجهة فقط):

- مندوب (أ) لا يستطيع رؤية أي طلب لمندوب (ب) — باستعلام SQL مباشر
- المندوب لا يرى إجماليات الشركة: أي `sum()` يعيد أرقامه هو فقط
- المندوب يرى صفّه فقط في `users`، ولا يرى `audit_log` إطلاقًا
- المندوب لا يستطيع تسجيل مسحوبات لنفسه، ولا إنشاء طلب لعميل مندوب آخر،
  ولا نسب طلب لمندوب آخر، ولا تعديل أو حذف طلب ليس له
- العرض `order_financials` يخضع لـ RLS (`security_invoker = true`)
- `profit = clientPrice − factoryCost`، `profitExVat = profit/1.15`،
  `repShare = profitExVat × 0.5` بأرقام حقيقية من `seed-orders.csv`
- تعديل أي مبلغ يُسجَّل في `audit_log` بالقيمة القديمة والجديدة ومن عدّلها

## المنطق المالي

كل المبالغ مُدخَلة **شاملة ضريبة القيمة المضافة 15%**. المعادلات في
`src/lib/finance.ts` ومكرّرة في العرض `order_financials` داخل قاعدة البيانات:

```
profit       = clientPrice − factoryCost
profitExVat  = profit / 1.15
vatDue       = profit − profitExVat
repShare     = profitExVat × (share_pct / 100)
companyShare = profitExVat − repShare
marginPct    = profit / clientPrice × 100
```

- النسبة الافتراضية للمندوب **50%**، مخزّنة في `users.share_pct` وقابلة
  للتعديل لكل مندوب من شاشة المستخدمين.
- كل طلب يحتفظ بلقطة `orders.rep_share_pct` وقت إنشائه، فتعديل نسبة المندوب
  لاحقًا لا يغيّر عمولات الطلبات القديمة.
- الحساب بدقة كاملة (`numeric(14,4)`) داخليًا، والتقريب للعرض فقط.
- `repBalance = Σ(حصص الطلبات المكتملة) − Σ(المسحوبات)` ولا يُخزَّن.

## الاستيراد من الإكسل

شاشة **الاستيراد** من ثلاث خطوات: رفع ← معاينة ← تأكيد. **لا يُكتب أي صف في
قاعدة البيانات قبل أن يراجع المشرف المعاينة ويحدّد قرار كل صف.**

الصفوف تُخزَّن مؤقتًا في `import_batches` / `import_rows` وتُصنَّف تلقائيًا:

| التصنيف | المعالجة |
|---|---|
| `adjustment` | قيد ربح بدون عميل ولا تكلفة (مثل الـ20,000) — لا يُستورد كطلب، بل كبند تسوية معلّق في `adjustments` |
| `missing_date` | يُستورد بـ `order_date = null` ويُعلَّم `needs_review` — لا تُخترع تواريخ |
| `conflict` | الربح المكتوب لا يطابق (السعر − التكلفة): يُستورد المحسوب من الجدول الرئيسي ويُدرج التعارض في التقرير |
| `duplicate` | نفس العميل بنفس المبلغ أكثر من مرة — لا تُستورد أي نسخة تلقائيًا، القرار للمشرف |
| `error` | صف تالف — يُتجاوز |

كل الحصص تُعاد حسابها بنسبة **50%**؛ حصص 60% في الملف القديم لا تُنسخ أبدًا.
المسحوبات القديمة (37,950 ريال) تُستورد اختياريًا كسجلات `withdrawals` بملاحظة
"رصيد مرحّل من الإكسل".

### ملاحظة على البيانات المرفقة

نصّ الوثيقة يذكر **11 صفقة بدون تاريخ**، لكن ملف `seed-orders.csv` المرفق
يحتوي فعليًا على **17 صفًا بلا تاريخ** (16 طلبًا + قيد الـ20,000). الاختبارات
تتحقق من الملف لأنه المصدر المعتمد للاستيراد، لا من النص.

## قرارات تصميمية تخالف حرفية الوثيقة

1. **`orders.order_date` قابل للقيمة الفارغة.** مخطط القسم 5 يعرّفه
   `not null`، لكن القسم 8 يفرض استيراد الصفقات بلا تاريخ بـ `null` دون
   اختراع تواريخ. الحاجة العملية تغلب، وأي طلب بلا تاريخ يُعلَّم تلقائيًا
   `needs_review`.
2. **PDF عبر طباعة المتصفح لا `@react-pdf/renderer`.** توليد PDF عربي على
   الخادم يحتاج تشكيل حروف (Arabic shaping) وخطوطًا مضمّنة، وهو هشّ على
   الخطة المجانية. صفحات التقارير (`/admin/reports/*`) مصمّمة للطباعة
   بتنسيق A4، والمتصفح يتكفّل بالتشكيل والاتجاه بشكل صحيح.
3. **`order_financials` عرض بـ `security_invoker = true`.** بدونه تُنفَّذ
   الاستعلامات بصلاحيات مالك العرض متجاوِزةً RLS بالكامل.
4. **تكلفة الطلبات المستوردة تُسجَّل كاملة في `cost_carton`** لأن الملف القديم
   لا يفصّل (كرتون/قالب/كليشة)، مع ملاحظة توضّح ذلك في `import_note`.

## التنبيهات

طبقة `src/lib/notifications.ts` تجريدية: كل قناة تنفّذ نفس الواجهة، وإضافة
واتساب لاحقًا لا تتطلب تعديل أي مستدعٍ. المفعّل الآن: إشعار داخل التطبيق
(جدول `notifications`) وبريد عبر Resend عند وجود `RESEND_API_KEY`.

الأحداث: طلب جديد، تغيّر مرحلة، هامش أقل من 10% (تنبيه فوري للمشرف)،
تحصيل متأخر 14 يومًا بعد الاستلام، ومرحلة عالقة أكثر من 7 أيام. الحدثان
الأخيران يعملان عبر `vercel.json` cron يوميًا الساعة 6 صباحًا.

## تحويل العملاء بين المندوبين

شاشة **إسناد العملاء** (`/admin/clients/assign`) للمشرف وحده. التحويل ينقل
ملكية العميل وطلباته المستقبلية للمندوب الجديد، بينما تبقى الطلبات السابقة
منسوبة لمندوبها الأصلي بعمولاتها كما هي — لا يُعاد احتساب عمولة سبق
استحقاقها.

هذا ليس اتفاقًا في الواجهة فقط: سياسات RLS تبني رؤية الطلبات على
`orders.rep_id` لا على `clients.owner_id`، والاختبارات في
`supabase/tests/01_rls_test.sql` تتحقق فعليًا من أربعة ضمانات: المندوب لا
يستطيع التنازل عن عميله، ولا الاستيلاء على عميل غيره، والمشرف يستطيع
التحويل، وبعد التحويل لا تتسرّب طلبات المندوب السابق للمندوب الجديد ولا
تضيع عمولته.
